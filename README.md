# Procedural Dungeon Generator & Roguelike System

Unity上で動作する、BSP（二分空間分割）アルゴリズムを用いたダンジョン自動生成システムおよび2Dローグライク基盤。

## 1. システム概要
- **アルゴリズム**: BSP（二分空間分割）ツリーによる動的空間分断 
- **データ駆動設計**: Prefab/Tilemapを自動解析・キャッシュするプリセット部屋構造
- **デバッグ環境**: Gizmosを用いたツリー構造のリアルタイム可視化ツール

## 2. 主要機能と技術的特徴
### ■ BSPアルゴリズムによる部屋生成と制御

- **面積優先分割ループ**: 最も面積の大きい領域の分割をし、分割後の領域を分割前の領域に葉として保持させる木構造を採用
  
  元来は単純なリスト構造でデータを管理していたが、BSP本来の強みを活かせていないことを知り、木構造に変更した
  
- **アスペクト比保護**: `partingMargin` による分断位置のクランプ

  分割位置の乱数の範囲によってバグが生じていたため、改善と共に分割位置を調節できるようにした

### ■ BspVisualizer（開発支援ツール）
- BSPの領域の分割がどのように行われているかを確認するために、導入したツール。Gizmosを用いて、ルートからの深さによって色合いを変更している。

### ■ シングルトンパターン（MonoBehaviour Singleton）によるアクセス最適化
全体から参照されるマネージャーに対し、インスタンス自身を静的に保持するシングルトン構造を適用。
シーン内の不要な検索コスト（`GameObject.Find` 等）を排除し、デバッグ環境やデータベースへの迅速なアクセスポンチを構築しました。a 

### ■ データ駆動型設計（Data-Driven Architecture）とデータ分離 //todo 誤用の可能性があるので確認
- **データ駆動**: 部屋の構造や生成パラメータをスクリプタブルオブジェクト（`RoomData` / `DungeonSettings`）として分離。コードを変更せずにエディタ上からダンジョン特性を調整可能な設計を実現。
- **静的・動的データの構造分離（Problem & Solution）**:
  - **課題**: 開発初期、動的オブジェクト（ドアやギミック等）を静的地形タイルと同一の配列で管理しようとした結果、生成時や上書き時にデータが欠損する設計上の欠陥に直面。
  - **解決**: 恒久的な地形を扱う `TerrainMap` と、状態を持つオブジェクトを扱う `GimmickMap` を明確に分離。データの欠損を防ぐとともに、後続の生成パイプライン（未使用ドアの壁化処理など）の安全性を確保した。

## 3. 技術的反省（Lessons Learned）

### ■ クラスの肥大化と密結合による保守性の低下
初期の開発段階において機能を高速に実装することを優先した結果、特定のクラスに処理が集約し、ファイルサイズの肥大化やクラス間の密結合を引き起こしました。これにより、一箇所の修正が他の機能へ意図しない影響を与えるリスクが高まり、コードの変更容易性が損なわれる課題に直面しました。

### ■ 基本情報技術者試験の学習と事前設計（UML）の重要性の実感
上記の課題に対し、資格学習を通じて習得した **UML（クラス図・シーケンス図）** やモジュール分割（関心の分離）の概念を振り返ることで、実装前の設計フェーズがいかに重要であるかを実体験として痛感しました。コードを書く前の抽象化とインターフェース設計の欠如が、保守性の低下を招いた根本原因であると分析しています。

### ■ 境界値・例外処理（ロバスト性）への配慮
特定パラメータ（大規模なマップサイズや不連続な区画設定）において、空間分割の判定が無限ループを引き起こすエッジケースが発生しました。ブラックリスト化（`HashSet`）やループ上限（Safeguard）を導入することで解決しましたが、初期設計段階から入力値の境界条件や異常系を想定した堅牢な設計を行う重要性を学びました。


## 4. 今後の展望（Future Work）

### ■ 静的地形データ（TerrainMap）に基づく経路探索（A*）の事前ベイク
本システムで分離・生成した `TerrainMap` の静的なグリッド構造を活用し、敵ユニットなどの動的オブジェクトが利用する A* 経路探索のノード情報を事前に計算（ベイク）・キャッシュする機構を実装します。これにより、毎フレームの走査コストを $O(M \times N)$ から大幅に削減します。

### ■ キャッシュ機構と両立する部屋データの動的変換（回転・反転）
`RoomDatabase` の遅延キャッシュ構造を拡張し、1つの `RoomData` プレハブから90度・180度回転および左右反転したデータを自動生成・保持するパイプラインを構築します。メモリ効率を維持したまま、ダンジョン構造のビジュアルバリエーションを4倍以上に拡張することを目指します。

### ■ 大学での学術的探求とシステムの再構築
今回の開発で得た「設計とアルゴリズム」の反省と気づきをベースに、大学進学後は情報工学・ソフトウェア工学を体系的に学びます。実装前にUMLによる厳密なアーキテクチャ設計を行い、今回の知見を活かしたより柔軟で拡張性の高いプロシージャル生成基盤の再構築に挑戦します。
